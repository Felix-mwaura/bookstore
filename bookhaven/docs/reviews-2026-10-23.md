## 2. A finding that shaped the work: the ratings on the site were invented

`books` has had two columns since before this engagement:

```
rating  numeric  default 4.5
reviews integer  default 0
```

In production, 16 titles carry 10 non-zero review counts that add up to **35,556**, with
averages between 4.5 and 4.8. No customer wrote any of them; the new-book endpoint used to
write `rating: 4.5` on every insert. `ProductCard` read both columns, and the admin Products
table displayed them, so a book with no reviews was shown as "4.5 ★ (4,100)".

Those numbers are now ignored everywhere:

- `toPublicBook()` no longer copies them (`app/lib/book-shape.js`).
- `getRelatedBooks()` used to order "You might also like" by `books.rating`, i.e. by
  fiction. It now orders by featured, then newest.
- The admin Products table shows the real average and count, or "No reviews".
- New books are inserted with `rating: null`, not 4.5.
- Structured data (`AggregateRating`) is emitted only when published reviews exist.

The columns themselves are untouched — dropping them is destructive and not mine to do —
but they are inert. Nothing reads them.

## 3. Schema and security model

### Table

`book_reviews`: `id`, `book_id` (bigint → `books.id`, cascade), `user_id` (uuid →
`auth.users.id`, cascade), `rating` (1–5), `title` (≤100), `review_text` (10–2,000),
`is_published`, `verified_purchase`, `reviewer_name`, `created_at`, `updated_at`.

Hard constraints: `unique (book_id, user_id)`, `check (rating between 1 and 5)`,
`check (char_length(review_text) between 10 and 2000)`, title and name lengths.

Indexes: partial on `(book_id, created_at desc)` and `(book_id, rating)` where published,
`(book_id)` where published for the aggregate, `(user_id)`, and `(created_at desc)` for
moderation.

### Aggregates

`book_rating_summary` — a `security_invoker` view over published rows only: average,
count and the 5→1 distribution. Computed on read. No rollup column to go stale after an
edit, a delete or an unpublish; the tests below prove each of those moves the numbers.

### Who may do what

| Actor | May |
| --- | --- |
| `anon` | read published reviews (and only the public columns) |
| any customer | read their own review, even if hidden |
| any customer | insert one review for themselves, edit their rating/words, delete their own review |
| admin (service role, behind `requireAdmin`) | read everything, publish/hide, delete |
| nobody | change `user_id`, `book_id`, `is_published`, `verified_purchase`, `reviewer_name` from a browser |

Three layers do that work, and all three are needed:

1. **RLS policies** decide which rows (`auth.uid() = user_id` on insert/update/delete).
2. **Column-level grants** decide which columns. `authenticated` may insert
   `(book_id, user_id, rating, title, review_text)` and update only
   `(rating, title, review_text)`. `user_id` is **not** in the anon SELECT grant, so a public
   query cannot read or correlate reviewer ids — and `select *` on the table fails loudly
   rather than leaking.
3. **A BEFORE trigger** derives `reviewer_name` (first name + last initial) and
   `verified_purchase` on every write, so even a client that sends
   `verified_purchase: true` gets it overwritten.

Because a customer cannot read `user_id`, they also cannot ask PostgREST "which row is
mine?". `my_book_review(book_id)` is a `SECURITY DEFINER` function scoped to `auth.uid()`
that returns only the caller's own row, and is executable by `authenticated` only. This
was not a design guess: the first version of the form updated by `user_id` and Postgres
refused it, which the SQL test caught immediately (see §5).

### Verified purchase

Derived in the database from `orders`: the order must be **`Delivered`** and its `items`
must contain the book. A paid-but-cancelled order earns nothing, and no browser can set the
flag. When an admin marks an order Delivered, `refresh_review_verification(user_id)` is
called from `/api/admin/orders` so existing reviews gain the badge immediately; the call is
service-role-only and failures are logged, never fatal.

## 4. Features, and the ones deliberately left out

Implemented: five-star keyboard-and-touch input with wording ("4 stars — Very good"), one
review per customer per book, write / edit / delete with confirmation, optional headline,
character counter, edited indicator, verified-purchase badge, average to one decimal,
distribution bars that double as filters, sort by recent / highest / lowest, star filters,
database-level pagination, empty states, sign-in-return-to-book flow, admin moderation with
search, status and star filters, publish/hide, remove, and real counts.

**Deferred, deliberately, and why:**

- **Helpful voting.** Needs a second table, its own RLS and an anti-gaming design. It was
  explicitly "only if it fits cleanly"; adding it now would double the surface area being
  reviewed in one change. The schema leaves room for it.
- **Review reporting.** Same reason, plus it needs a moderator queue that has somewhere to
  go. Not built rather than half-built.
- **Profanity filtering / spam scoring.** Only authentication, one-per-customer, length
  limits and rate-free moderation exist. There is no automated content classifier.
- **Draft (unpublished-by-author) reviews.** Only moderation hides a review; authors always
  create published ones.

| `npx next build` | PASS (fonts shimmed locally, `app/layout.js` restored; `git diff` empty) |
| `node scripts/smoke.mjs` | 24 pass, 9 skip — identical to the pre-change baseline |

The SQL test is not decorative. It includes, and passes:

- a customer inserting a review as **someone else** → refused by RLS;
- six separate attempts to set `verified_purchase`, `is_published`, `reviewer_name`,
  `user_id` or `book_id` from a browser → all refused by the column grants;
- ratings `0 / 6 / -1 / 99`, a 9-character review, a 2,001-character review and a
  101-character headline → all refused by the CHECK constraints;
- a second review for the same book → refused by the unique constraint;
- an anonymous visitor reading a hidden review, reading `user_id`, or writing anything →
  refused; the hidden review is absent from the public summary;
- Bob editing and deleting Alice's review by id → zero rows affected, Alice's review intact;
- Alice editing her own review → rating changes, owner and badge preserved, `updated_at`
  moves;
- the aggregate after publish, edit, unpublish and delete → correct every time, and a book
  with no reviews is simply absent from the view (no divide-by-zero);
- an order becoming Delivered → badge appears, and a customer cannot call the function;
- deleting a book → its reviews go with it;
- re-running the migration → no change, one trigger.

### Not tested, and why

- **Nothing was rendered against the live database.** This sandbox cannot reach
  `*.supabase.co` (connections are refused), so no page was loaded with real reviews. The
  build and the API smoke tests pass, but the first real render will be on the preview
  deployment. The *schema* was verified live (§6); the *page* was not.
- **No review has been written end to end by a real signed-in customer.** That needs a
  browser session against the deployed app, which this environment cannot create.
- **No browser.** No device, viewport, screen-reader or Lighthouse run. Keyboard behaviour
  is by construction (native radio group, real labelled inputs), not by observation.
- **No concurrent-write test** (two tabs submitting at once). The unique constraint is the
  guarantee; it is not timing-tested.

## 6. Applied — and one thing the live database taught me

The migration was applied to `luniopceavtkljywukyi` on 2026-10-23 and recorded as version
`20261023162927`. Verified against the live project afterwards:

| Check | Result |
| --- | --- |
| `to_regclass('public.book_reviews')` | `book_reviews` |
| `relrowsecurity` on `book_reviews` | `true` |
| policies on `book_reviews` | 6 |
| `book_reviews_before_write` trigger | present, enabled |
| `has_column_privilege('anon','book_reviews','user_id','SELECT')` | **false** |
| `has_column_privilege('anon','book_reviews','review_text','SELECT')` | true |
| `has_column_privilege('authenticated','book_reviews','is_published','UPDATE')` | **false** |
| `has_column_privilege('authenticated','book_reviews','verified_purchase','UPDATE')` | **false** |
| `has_column_privilege('authenticated','book_reviews','user_id','UPDATE')` | **false** |
| `has_column_privilege('authenticated','book_reviews','rating','UPDATE')` | true |
| `has_table_privilege('anon','book_reviews','INSERT')` | **false** |
| `has_function_privilege('authenticated','my_book_review(bigint)','EXECUTE')` | true |
| `has_function_privilege('anon','my_book_review(bigint)','EXECUTE')` | **false** (after a fix) |
| `has_function_privilege('anon','customer_has_delivered(uuid,bigint)','EXECUTE')` | false |

**What the live project caught that the local tests could not:** Supabase's default
privileges grant `EXECUTE` on new functions in `public` to `anon` and `authenticated`
explicitly, and `revoke ... from public` does not undo an explicit grant. `my_book_review`
was therefore callable by `anon` even though the function, the code and the local Postgres
test all behaved as though it was not. It was revoked on the live project and the
`revoke` is now in the migration file, so a database rebuilt from scratch ends up matching.
No data was exposed — the function filters on `auth.uid()`, which is null for an anonymous
caller, so it returned zero rows — but a privilege that exists by accident is still a
privilege that exists.

Nothing in the migration reads or writes an existing row, so it could not change
catalogue, order or payment behaviour. It is wrapped in `begin/commit` and every statement
is idempotent.
