# Genres: a shelf you can edit

28 October 2026

Two briefs arrived together: one about the homepage genre control, one about
letting the admin add and remove genres. They turn out to be the same problem
seen from both ends, so they are one change.

## What was wrong

**Genres were a constant.** `app/lib/categories.js` exported an array of eight
names, and everything that lists genres imported it: the homepage deck, the
header nav and search filter, the catalogue sidebar and filter sheet, the
category pages, and — separately, as a second copy — the admin's book form.
Adding a genre was a code change and a deploy, in two places.

**The homepage control swallowed taps.** The genre deck starts a swipe on any
`pointerdown` inside its region, and the arrows and dots are inside that
region. Once the pointer had drifted 8px sideways, the deck decided the press
was a swipe and cancelled the click that followed. On a touch screen that
drift is ordinary — a thumb rolls a few pixels on every tap — so a tap on a
dot or a neighbouring card could do nothing at all, and the next tap often
worked because the deck had moved. That is exactly the reported symptom:
"clicking a genre does not reliably respond, and switching to another one
sometimes does nothing."

A second, smaller defect in the same place: the click suppression was cleared
on a zero-delay timer. Some browsers dispatch `click` in a later task than
`pointerup`, so the timer could clear the suppression before the click
arrived — a completed swipe would then navigate.

## What changed

**Genres are rows.** `20261028120000_genres.sql` creates `public.genres`
(`id`, `name`, `slug`, `created_at`, `created_by`), unique on `lower(btrim(name))`
and on `slug`, seeded with the eight existing names plus any category a book
already uses. Reads are public; there is no insert/update/delete policy at
all, so the anon key can list genres and nothing else. The admin API uses the
service role after `requireAdmin`.

**Deletion cannot orphan a book.** A `before delete` trigger counts the books
naming the genre and raises if there are any. The route checks first so the
admin gets a sentence rather than a database error, but the trigger is what
makes it true — a count-then-delete in application code is a race.

**The storefront reads the list, and cannot fail.** `app/lib/genres-data.js`
is the only reader. It is cached per request and for a minute across requests,
times out after 1.5s, backs off for 30s after a failure, and returns the
built-in list if the table is missing, empty, or unreachable. A genre list is
navigation; navigation is not allowed to depend on a query succeeding — the
lesson from the preview outage earlier the same week.

The list reaches client components through `GenreProvider` in the root
layout. `HomeClient`, `StoreHeader` and `CatalogueControls` read it from
there instead of importing the constant. Category pages resolve slugs against
it, so `/category/business` works the moment the genre exists, and an unknown
slug is still a 404.

**The admin gets a Genres tab.** Add a name; it is trimmed, length-checked,
slugged, and refused if it duplicates an existing name in any case or
spelling, or if the name is the reserved `All`. Remove one; the row shows how
many books are on it and refuses while that is more than zero. The book form
now asks `/api/admin/genres` for its options, falling back to the built-in
list until the response lands, so a new genre appears there without a deploy.

**The deck stops eating taps.** A press on an arrow or a dot never arms a
swipe. A press clears the previous gesture's suppression. The click that ends
a swipe is swallowed by a capture handler, which is also what clears the flag
— there is no timer deciding whether a tap counts. The active index is
clamped to the list, so a genre removed while the deck is mounted cannot
leave an empty stage.

## Applied

The migration was applied to the live project (`luniopceavtkljywukyi`) on
28 October. The table holds the eight seeded genres, distributed over the 16
books exactly as the categories were (Fiction 7, Finance 2, Self-Help 2, the
rest 1 each); RLS is on with a single SELECT policy; the delete trigger is
installed and refuses to remove a genre that still has books. Checked against
the database itself:

- deleting `fiction` raises `foreign_key_violation` and the row survives;
- a genre with no books inserts and deletes cleanly;
- `'  fiction '` is rejected by the case- and space-insensitive unique index;
- the table has exactly one policy, and it is SELECT.

## Card art

A genre can carry its own picture. The admin picks one when adding a genre,
and can replace or remove it later from the row it belongs to.

**Where it lives.** The file goes to the same public bucket as book covers
(`book-covers`), under `genres/<uuid>.<ext>` — the bucket is already public,
already capped at 2 MB and already restricted to JPG/PNG/WebP, and its storage
policies already allow exactly administrators to write. A second bucket would
have meant re-deriving those policies for no gain. The row stores the public
URL in `genres.image_url`.

**What is refused.** The route accepts a URL only if it starts with this
project's public storage prefix and the path under it is `genres/<file>` — no
other host, no other folder, no `..`, no query string. The storefront checks
again on the way out (`safeImageUrl`): only an `https:` URL or a path inside
this app reaches `<Image src>`, so a row edited by hand in the SQL editor
cannot turn the homepage into a request to somebody else's server, or smuggle
`javascript:`/`data:` into an attribute. Both rules are tested.

**What happens to the old file.** Upload first, save second: a genre is never
created pointing at an image that did not arrive, and a failed save deletes
the orphan. Replacing or clearing an image deletes the previous file once the
database has accepted the new value; deleting a genre deletes its art. All of
that is best effort — a leftover file is untidy, never broken.

**The fallback chain.** Uploaded art → the artwork bundled in `app/lib/genres.js`
for that slug (the eight launch genres have generated still lifes) → the plain
navy panel with the genre's initial. A card whose image 404s falls back to the
same panel rather than showing a broken-image glyph.

**Applied.** `20261028160000_genre_images.sql` (`add column if not exists
image_url text`) is applied to `luniopceavtkljywukyi`; the column is present
and nullable, so every existing row keeps its built-in art.

Verified against a fixture database that returned an image URL for one genre
and `javascript:alert(1)` for another: the homepage deck rendered the first
through `/_next/image` and dropped the second entirely. Not verified: an
actual upload through the admin UI — that needs a signed-in administrator and
a browser, neither of which exists here. The storage policy it depends on was
read from the database and does allow admins to insert into this bucket.
